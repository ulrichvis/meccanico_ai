# Frontend internationalization

## Objective

Meccanico IA uses English as its official development language and ships the frontend in English and Italian from the first release. Localization is part of the Phase 1 foundation, not a later retrofit.

## Supported locales

| Locale | Role |
|---|---|
| `en` | Default locale and canonical fallback. |
| `it` | Required Italian frontend translation. |

Additional locales may be introduced later without changing domain models or API contracts.

## Catalog structure

```text
messages/
├── en.json
└── it.json
```

Both catalogs must have identical key paths. Keys are semantic, hierarchical, and written in English:

```json
{
  "common": {
    "actions": {
      "cancel": "Cancel",
      "save": "Save"
    }
  },
  "upload": {
    "dropzone": {
      "title": "Upload a PDF",
      "hint": "Drag and drop a file or choose one"
    }
  }
}
```

The Italian catalog uses the same keys with Italian values. Components request keys through the localization adapter; they do not import JSON files directly.

## Locale resolution

Routes remain language-neutral:

```text
/
/upload
/cases
```

Resolution order:

1. saved explicit user preference;
2. supported browser language preference;
3. English fallback.

The language selector replaces displayed text without navigation or URL changes. The explicit choice is stored locally and takes precedence over future automatic detection.

## Translation boundary

Translate all user-facing content:

- navigation, headings, labels, buttons, and help text;
- form validation and user-visible errors;
- status labels, notifications, and progress messages;
- empty, loading, success, and failure states;
- accessibility labels and metadata;
- dates, numbers, and pluralized messages.

Keep these items in English or in their original technical form:

- source code, identifiers, comments, and technical documentation;
- logs and internal error codes;
- API fields, database enums, and storage values;
- DTC codes, part numbers, units, and manufacturer terminology;
- original source evidence excerpts.

Do not use runtime machine translation for product UI. Locale files provide deterministic, reviewed wording. Automatic translation in this project means automatic selection and rendering of the appropriate maintained catalog.

## Error handling

Services return stable English error codes, not display sentences. The frontend maps each known code to a localized message. Unknown errors use a localized generic fallback while technical details remain in server logs.

Example:

```ts
type UploadErrorCode =
  | "UPLOAD_INVALID_TYPE"
  | "UPLOAD_TOO_LARGE"
  | "UPLOAD_STORAGE_FAILED";
```

## Formatting

Use locale-aware formatters for dates, times, numbers, percentages, and pluralization. Store dates in UTC and values in language-neutral forms. Localization occurs only at presentation time.

## Verification

The planned `pnpm i18n:check` command must fail when:

- a catalog contains invalid JSON;
- a key exists in only one supported catalog;
- a value has the wrong structural type;
- an interpolation variable differs between locales.

Manual verification for each frontend feature must cover English and Italian on the same route, the language selector, English fallback, and user-visible error states.

## Adding a message

1. Choose a semantic key in the relevant namespace.
2. Add the English value to `messages/en.json`.
3. Add the Italian value to `messages/it.json`.
4. Reference the key from the component or page.
5. Run `pnpm i18n:check`, lint, type checking, and the build.
6. Verify the feature manually in both locales.
